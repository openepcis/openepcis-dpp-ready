# IDTA AAS submodel semanticIds — upstream registry

**Status:** Registry (curated by hand from the published IDTA templates) • **Layer:** 2 (sectoral upstream profile — Industrial Digital Twin Association / Industrie 4.0) • **Licence:** CC BY 4.0 (upstream templates)

This module records the **Asset Administration Shell semanticIds the OpenEPCIS
AAS service emits** when it derives an AAS environment (IEC 63278) from GS1 Web
Vocabulary master data, and anchors each one to the GS1 term the builder
actually reads. It is the bridge between the two worlds: on one side the
resolver-served GS1 master data (Product, Organization, Place), on the other
the IDTA submodel templates that industrial consumers of an AAS expect. The
authoritative source is upstream:

- **Template catalogue:** <https://industrialdigitaltwin.org/en/content-hub/submodels>
- **Template repository:** <https://github.com/admin-shell-io/submodel-templates>

Three templates cover the emitted surface: **IDTA 02006-3-0 Digital Nameplate
for Industrial Equipment (3.0)**, **IDTA 02002-1-0 ContactInformations (1.0)**
(whose semanticIds still live in upstream's legacy `zvei` namespace, preserved
verbatim), and the **IDTA DPP Metadata** submodel (`dppMetadata/1`), whose
header properties are identified as `{submodel semanticId}/{idShort}`.

Unlike the `gs1-rail` and `cirpass2-eudpp` mirrors there is nothing to sync:
IDTA publishes AASX/JSON template packages, not RDF, so `ontology/idta-aas.ttl`
is curated by hand against the published templates. Upstream identity is still
preserved wherever upstream has one — semanticIds that are IRIs
(`admin-shell.io`) appear verbatim as subjects, and nothing is rebranded under
`ref.openepcis.io`. The nameplate and contact elements, however, are identified
by **IRDIs** (IEC CDD `0112/2///61987#…`, ECLASS `0173-1#02-…`), which are not
IRIs and cannot be RDF subjects; those elements carry a local node under this
module's namespace with the verbatim IRDI in `skos:notation` — the same move
`masterdata/served-fields` makes for its resolver-specific field shapes.

## What this module ships

| File | Provenance | Purpose |
|---|---|---|
| `ontology/idta-aas.ttl` | Curated by hand from the published IDTA templates | Source of truth: the emitted semanticIds, verbatim, with graded SKOS mappings to the GS1 terms the builders read. |
| `json/idta-aas.json` | Generated by `pnpm build:json` from the TTL | Vocabulary browser data for ref.openepcis.io. |

No JSON-LD context and no SHACL are shipped: AAS payloads are not JSON-LD, and
the relationship is alignment, not adoption — the semanticIds never appear in
OpenEPCIS EPCIS or passport payloads.

## The identity bridge

The load-bearing mapping is the identity: the **canonical GS1 Digital Link URI
(id.gs1.org)** is emitted as the AAS `globalAssetId`, as the nameplate's
`URIOfTheProduct`, and as the DPP Metadata header's `uniqueProductIdentifier`
and `digitalProductPassportId` — one identity at every AAS anchor point, all
mapped `skos:exactMatch` to `gs1:productID`. In the GS1 rendering that URI is
the JSON-LD node identity (`@id`); `gs1:productID` is the property stand-in
this project uses wherever identity must appear as a property, the same
convention the EN 18223 envelope follows.

## Scope

The registry covers exactly the surface the phase-0 builders populate from GS1
master data — deliberately **not** a full mapping of the templates. The Digital
Nameplate alone defines far more elements (markings, firmware versions, asset
specifics) than GS1 master data can source; listing them here would assert
mappings nobody emits. When the builders grow, the registry grows with them.

## Migration path

The link type routing consumers to the AAS representation is the provisional
`https://ref.openepcis.io/voc/aas` (see [`voc/`](../../../voc/ontology/openepcis-linktypes.ttl)),
because the GS1 Web Vocabulary defines no AAS link type yet. As soon as GS1
ratifies an official one, resolvers emit both link types in parallel (dual
emission) for a transition window and then migrate to the GS1 term. The
semanticIds in this module are unaffected by that migration — they belong to
IDTA, not GS1.

## Regeneration

```bash
pnpm run build:json   # regenerates json/idta-aas.json from the TTL
```

When IDTA releases a new template version the builders adopt: update the
semanticIds in `ontology/idta-aas.ttl` by hand, bump `VERSION`, and record the
delta in `CHANGELOG.md`.
